# نسخه‌های نرم‌افزار و فایل HEX

## گردش کار

در بخش «نسخه‌های نرم‌افزار»، نام و شماره نسخه الزامی است؛ مدل دستگاه، مدل/نسخه برد و توضیحات اختیاری‌اند. فایل HEX را می‌توان هم‌زمان با تعریف نسخه یا بعداً کنار همان نسخه بارگذاری کرد. فایل و مشخصات نسخه پس از ثبت قابل جایگزینی نیستند. برای فایل متفاوت، نسخه جدید تعریف شود. این بخش کاتالوگ نسخه‌هاست؛ نصب روی دستگاه یا تبدیل خودکار متن قدیمی «نسخه نرم‌افزار» شناسنامه به ارتباط جدید انجام نمی‌دهد.

هویت یکتا از نام، شماره نسخه، مدل دستگاه و برد، پس از یکسان‌سازی ارقام، فاصله‌ها و حروف محاسبه می‌شود. شماره نسخه آزاد است و الزام به SemVer ندارد. نسخه‌های متفاوت برای بردها یا مدل‌های متفاوت مستقل‌اند. تغییر نام فایل به‌تنهایی نسخه جدید محسوب نمی‌شود.

فایل باید Intel HEX متنی، غیرخالی و حداکثر ۱۰ MiB باشد. سرور پسوند، اندازه، شکل رکورد، طول، نوع رکورد و checksum هر خط، وجود داده و رکورد پایان را کنترل می‌کند. بایت‌های فایل عیناً حفظ می‌شوند. این بررسی صرفاً یکپارچگی قالب است؛ بررسی سازگاری آدرس‌ها/پردازنده، عملکرد، ایمنی پزشکی یا مجوز استفاده نیست. فایل در سامانه اجرا یا روی دستگاه نصب نمی‌شود.

## داده و امنیت

- مشخصات نسخه در `records` با نوع `firmware` و شناسه مشتق‌شده از هویت یکتا ذخیره می‌شود.
- بایت‌های فایل در R2 خصوصی با کلید تصادفی برای هر تلاش بارگذاری؛ مشخصات فایل در جدول `firmware_files` در D1 نگهداری می‌شود. هر نسخه فقط یک فایل دارد و پایگاه داده این قید را اعمال می‌کند.
- SHA-256 از بایت‌های اصلی در سرور محاسبه می‌شود. هنگام دانلود اندازه و هش دوباره بررسی می‌شوند. خطا یا مغایرت، دانلود را متوقف می‌کند. SHA-256 امضای دیجیتال یا تأیید نویسنده نیست.
- مسیر فایل، URL عمومی یا کلید R2 به مرورگر داده نمی‌شود. دانلود از مسیر احراز هویت‌شده با `Content-Disposition: attachment`، `nosniff` و `private, no-store` انجام می‌شود.
- مجوز مستقل `firmware` برای مشاهده/دانلود و ثبت/بارگذاری وجود دارد. مالک دسترسی کامل دارد؛ الگوی «مهندسی نرم‌افزار» اضافه شده است. مجوز حساب‌های قبلی خودکار تغییر نمی‌کند.
- ساخت نسخه و اتصال فایل هر کدام همراه سابقه ممیزی شامل هویت ثبت‌کننده و زمان سرور ثبت می‌شوند. API عمومی رکوردها اجازه ایجاد یا ویرایش این نوع را نمی‌دهد.

## تراکنش و خطا

ثبت مشخصات نسخه و بارگذاری فایل دو مرحله‌اند. اگر نسخه ذخیره شود ولی فایل ناموفق باشد، نسخه باقی می‌ماند و کاربر می‌تواند از «بارگذاری HEX» ادامه دهد. در خطای ارتباط پس از ثبت نسخه، پیش از تکرار فهرست تازه شود؛ قید هویت یکتا مانع ساخت نسخه تکراری است.

R2 و D1 تراکنش مشترک ندارند. ابتدا شیء با کلید تازه بارگذاری می‌شود، سپس مشخصات فایل و ممیزی در یک `batch` ثبت می‌شوند. در شکست، سرور ارتباط را دوباره می‌خواند: اگر همان شیء متصل شده باشد، موفقیت بازگردانده می‌شود؛ اگر قطعاً متصل نیست فقط همان شیء تازه پاک می‌شود. اگر وضعیت پایگاه داده قابل تشخیص نباشد، شیء برای جلوگیری از حذف فایل معتبر باقی می‌ماند. ممکن است در این حالت شیء بدون ارتباط باقی بماند؛ پاکسازی مدیریتی بعدی باید با تطبیق دقیق پایگاه داده انجام شود. فایل موجود هیچ‌وقت برای بارگذاری جدید حذف نمی‌شود.

مهاجرت افزایشی `0002_previous_toad_men.sql` جدول فایل‌ها و محدودیت یکتایی را ایجاد می‌کند؛ مهاجرت‌های قبلی دست‌نخورده‌اند. پشتیبان کامل نیازمند هر دو داده D1 و فایل‌های R2 است؛ خروجی JSON صفحه به‌تنهایی پشتیبان فایل HEX نیست.

## بررسی توسعه

`node tests/firmware.cjs`: API واقعی با SQLite موقت و شبیه‌ساز بایت‌محور R2؛ اعتبار فایل، محدودیت بدنه، یکتایی نسخه، دانلود عین بایت‌های ورودی، جلوگیری از جایگزینی، رقابت هم‌زمان، بازیابی خطای بارگذاری، قطع پاسخ پس از ثبت، هش و دسترسی‌ها. هیچ فایل آزمونی در محیط شرکت بارگذاری نمی‌شود.

مراجع فنی: [Intel HEX / Arm](https://support.arm.com/documentation/ka003292/latest)، [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
