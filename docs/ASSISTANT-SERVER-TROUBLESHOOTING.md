# مدل در تنظیمات تست می‌شود اما در دستیار دیده نمی‌شود

تنظیمات و آزمون مدل، جدول `llm_configs` را می‌خوانند. تاریخچه چت و پیشنهادهای اجرا به‌ترتیب به `assistant_turns` و `assistant_actions` وابسته‌اند. در نسخه قبلی شکست هر کدام از دو مورد دوم کل پاسخ GET /api/assistant را ناموفق می‌کرد و فهرست مدل‌ها نیز در رابط کاربری نمایش داده نمی‌شد.

اصلاح فعلی فهرست مدل‌ها را از `/api/assistant/profiles` مستقلاً دریافت می‌کند. این مسیر با همان حساب ورود و از همان جدول پروفایل‌ها کار می‌کند و هیچ توکنی برنمی‌گرداند. مسیر قدیمی برای سازگاری MCP همچنان فهرست را در پاسخ موفق خود دارد.

روی سرور شرکت:
1. نسخه جدید شاخه `sites/nafasyar-trace` را دریافت، build و اجرا کنید. فایل‌های دیتابیس و کلید رمزگذاری موجود حفظ شوند.
2. در نشست ورود، پاسخ `/api/assistant/profiles` باید دو پروفایل ذخیره‌شده همان سرور را برگرداند.
3. اگر `/api/assistant` پیام جدول سابقه بدهد، مهاجرت اجرا‌نشده `drizzle/0010_warm_hawkeye.sql` را طبق روال مهاجرت همان سرور اعمال کنید.
4. اگر پیام جدول فرمان‌ها بدهد، مهاجرت اجرا‌نشده `drizzle/0012_lively_bloodscream.sql` را طبق روال مهاجرت همان سرور اعمال کنید. وضعیت مهاجرت‌ها و طرح دیتابیس را قبل از اجرا تطبیق دهید؛ مهاجرت اجراشده را کورکورانه تکرار نکنید.
5. برای خطای دیگری، وضعیت HTTP و خطای سرور همان مسیر را بررسی کنید. فهرست مدل‌ها نباید به دریافت موفق تاریخچه وابسته باشد.

این اصلاح جدول را خودکار حذف، بازسازی یا seed نمی‌کند و مدل/کلید ذخیره‌شده را تغییر نمی‌دهد. موفقیت آزمون مدل، سلامت جدول‌های داخلی چت را اثبات نمی‌کند. از طرف دیگر، بدون لاگ سرور نمی‌توان نبودن مهاجرت را علت قطعی دانست.


## ثبت و دریافت خطای دستیار (نسخه ۶ اکتبر ۲۰۲۶)

نسخه جدید در خطای داخلی `/api/assistant` و `/api/assistant/profiles` یک UUID در پیام کاربر نشان می‌دهد. همان UUID در یک خط JSON با پیشوند `[assistant-error]` توسط `console.error` چاپ می‌شود. این گزارش در stderr فرایند برنامه است؛ برنامه فایل لاگ مستقل یا جدول لاگ نمی‌سازد. محل نگهداری و ماندگاری را سرویس اجراکننده سرور تعیین می‌کند.

پس از دریافت نسخه، build و راه‌اندازی مجدد، همان حساب را باز کنید و خطا را یک بار تکرار کنید. در لاگ برنامه، کد پیگیری تصویر را جست‌وجو کنید. خط JSON متناظر برای بررسی کافی است. لاگ access وب‌سرور معمولاً تنها کد HTTP را دارد و جای این گزارش نیست.

بسته به روش اجرای واقعی سرور، یکی از این دستورها مناسب است؛ نام داخل `<...>` را با نام واقعی جایگزین کنید:

- PM2: `pm2 logs <app-name> --lines 200` (مسیر فایل‌های خروجی/خطا با `pm2 describe <app-name>` مشخص می‌شود).
- Docker: `docker logs --tail 200 <container-name>` در صورتی که logging driver دسترسی به لاگ را پشتیبانی کند.
- systemd: `journalctl -u <service-name> -n 200 --no-pager` در صورتی که خروجی سرویس به journal هدایت شود.
- اجرای مستقیم Node: خروجی همان ترمینال/فرایند؛ در صورت redirect، فایلی که در فرمان اجرا تعیین شده است.

گزارش شامل `reference`, `method`, `route`, `stage`, `reason`, `tables`, `columns`, `codes` است. `profiles`، `history` و `actions` به‌ترتیب خواندن مدل‌ها، سابقه و فرمان‌ها هستند. علت می‌تواند `missing_table`، `missing_column`، `database_locked`، `database_readonly`، `invalid_json`، `binding_error` یا `runtime_type_error` باشد؛ `internal_error` یعنی دسته دقیق‌تر از خطای دریافت‌شده قابل تشخیص نبوده و رفع علت هنوز تأیید نشده است.

این گزارش عمداً متن خام exception/SQL، پارامترهای query، مسیرهای فایل، کلیدهای API و محتوای گفتگو را ثبت نمی‌کند. فقط نام‌های شناخته‌شده طرح دیتابیس و کدهای مجاز خطا گزارش می‌شوند. هیچ تغییر خودکار داده، مهاجرت یا بازنشانی انجام نمی‌شود.
